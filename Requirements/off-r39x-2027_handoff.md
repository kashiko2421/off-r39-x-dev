# 8. 購入情報の安全性

購入情報のロスト防止を最重要要件とする。

## 基本方針

Stripeへ遷移する前に、DBに注文を作成する。

```text
Order
status = pending
↓
Stripe Checkout
↓
Stripe Webhook
↓
Order
status = paid
```

ブラウザがStripeから成功ページへ戻ったことだけでは購入確定にしない。

**Stripe Webhookを購入確定の基準とする。**

## 冪等性

同じStripe Webhookが複数回来ても、

- 注文が二重確定されない
- チケットが二重発行されない
- メールが必要以上に重複送信されない

ようにする。

例:

- `stripe_event_id` UNIQUE
- `stripe_checkout_session_id` UNIQUE
- `stripe_payment_intent_id` UNIQUE

等を利用。

## Transaction

以下の重要処理はDB Transaction内で行う。

```text
Orderをpaidにする
↓
Ticketを作成する
↓
関連レコードを更新する
```

途中失敗時は中途半端な状態を残さない。

# 11. QRコード仕様

QRコードには単純なDB連番IDをそのまま含めない。

十分に推測困難なランダムトークンを使用する。

必要に応じてDBにはトークンそのものではなくハッシュを保持する設計も検討する。

QR種別:

```text
ENTRY
KARAOKE
```

受付側はQRを読み取った後、必ずAPIを通して有効性を確認する。

# 14. カラオケ予約ページUI

最初から細かい時間枠を大量に表示するのではなく、

> **日付 → 1時間単位の空き状況 → 具体的な予約枠**

の順に選ぶ。

表示例:

```text
9/16

16:00〜 ◎
17:00〜 ○
18:00〜 △
19:00〜 ×
```

## 空き状況表示

1時間3枠を前提とする。

| 空き枠数 | 表示 |
|---:|:---:|
| 3枠 | ◎ |
| 2枠 | ○ |
| 1枠 | △ |
| 0枠 | × |

ユーザーが例えば `17:00〜 ○` を選ぶと、具体的な枠を表示する。

例:

```text
17:00〜17:15 予約可能
17:20〜17:35 売り切れ
17:40〜17:55 予約可能
```

スマートフォンを主に考え、1時間単位の選択UIはカードや横スクロール等を想定。

詳細枠は同じページ内で展開する設計を優先。

# 17. カラオケの二重販売防止

同じ時間枠を複数人へ販売してはいけない。

ユーザーが購入開始した時点で枠を一時的に仮押さえする。

概念:

```text
AVAILABLE
↓
HELD
↓
SOLD
```

Stripe Checkoutを途中離脱した場合などは、一定時間後に仮押さえを解除する。

```text
HELD
↓
期限切れ
↓
AVAILABLE
```

具体的な保持時間は仕様書作成時に決定する。
