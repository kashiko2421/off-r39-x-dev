# off r39'x システム Project Constitution

## 1. 文書の目的

本書は、off r39'x のWebサービスおよび関連運用システムにおける、最上位の設計原則・仕様統治ルール・実装原則を定義する。

本書は個別機能の詳細仕様を定義するものではない。注文、決済、入場チケット、カラオケ、グッズ、認証、管理画面、受付、API、DB等の具体的な業務ルールおよび技術契約は、それぞれのAuthorityを持つ仕様書で定義する。

本書の目的は、長期間にわたって仕様書と実装が増加しても、以下を維持することである。

- システム全体の一貫性
- 仕様のSingle Source of Truth
- 重要なデータ整合性
- 安全な決済・販売・受付
- 明確な責務分離
- 監査可能な運用
- AIエージェントが安全に実装できる構造
- 将来変更に耐えられる仕様管理

---

## 2. 適用範囲

### PRJ-001 完成形を仕様化する

本プロジェクトの正式仕様書は、システムの完成形および長期運用時の期待動作を定義しなければならない。

実装フェーズ、開発順序、段階的リリース範囲、短期的な実装対象は正式仕様の内容を変更してはならない。

実装範囲は、Codexその他の実装担当へ渡す実装指示によって制御する。

### PRJ-002 システムの主要領域

本システムは少なくとも、以下の領域から構成され得る。

- 公開Webサイト
- アカウント・認証・プロフィール
- 商品・販売
- 注文
- 決済・返金
- 入場チケット
- カラオケ予約
- グッズ・在庫・会場受け渡し
- マイページ
- 管理画面
- スタッフ向け受付
- QR・電子チケット検証
- メール・通知
- 監査・運用
- API
- データベース
- 外部サービス連携

各領域の詳細は、それぞれのAuthority仕様で定義する。

### PRJ-003 イベント再利用性

本システムは当面の対象イベントに最適化してよいが、同系統イベントへの将来的な再利用を不必要に妨げる設計としてはならない。

ただし、汎用イベントプラットフォーム化や過剰なマルチテナント化を目的としてはならない。

イベント概念をどのデータへ明示的に関連付けるかはDomain仕様およびDATA仕様で決定する。

## 3. 規範表現

本仕様書群では、要件の強さを以下の日本語で表現する。

| 表現 | 意味 |
|---|---|
| **必須** | 実装・運用が従わなければならない要件 |
| **原則** | 特段の合理的理由がない限り従う要件 |
| **許容** | 実装または運用上選択してよい事項 |

「例」「例示」「参考」「イメージ」と明記された記述は、明示的に規範要件へ参照されない限り、必須仕様として扱ってはならない。

## 4. 仕様書体系とSingle Source of Truth

### PRJ-010 正式仕様の所在

承認済みの仕様ファイルを、実装に対するSingle Source of Truthとする。

チャット履歴、口頭説明、実装上の推測、既存コードの偶発的挙動は、承認済み仕様を上書きするAuthorityを持たない。

### PRJ-011 1 Chat = 1 Spec File

仕様策定は原則として、1つのChatで1つの仕様ファイルを完成させる。

各Chatは、担当する仕様書の責任範囲に集中し、他領域のAuthorityを持つルールを重複定義してはならない。

### PRJ-012 仕様ファイルの責任

各仕様ファイルは、以下を明確にしなければならない。

- 目的
- 適用範囲
- 責任外
- Authority
- 関連仕様
- 規範仕様
- 状態モデル
- 例外・異常系
- 整合性条件
- セキュリティ上の制約
- 受け入れ条件
- 未確定事項
- Decision Log
- Handoff

必要のない項目は省略可能だが、責任境界は明確でなければならない。

## 5. Authorityモデル

### PRJ-020 Constitutionの優先順位

本書は、全仕様書および実装が従う最上位のAuthorityである。

下位仕様は、本書に反する規範を定義してはならない。

### PRJ-021 概念ごとのAuthority

Constitution以外の仕様書間では、ファイルの新旧、具体性、文章量ではなく、対象概念に対するAuthorityによって正を決定する。

一つのAuthority Keyには、原則として一つの所有仕様を割り当てる。

例:

- `order.lifecycle`
- `payment.lifecycle`
- `ticket.lifecycle`
- `karaoke.slot`
- `karaoke.reservation`
- `goods.inventory`
- `checkin`
- `identity`
- `authorization`
- `database.physical`
- `api.contract`

最終的なAuthority Registryは仕様インデックスで管理する。

### PRJ-022 他領域の再定義禁止

Authorityを持たない仕様書は、他領域のルールを再定義してはならない。

必要な場合はAuthorityを持つ仕様IDを参照する。

### PRJ-023 仕様矛盾の扱い

仕様矛盾を発見した場合、暗黙に読み替えたり、一方を自動採用したりしてはならない。

矛盾は明示的なSpec Conflictとして記録し、Authorityと影響範囲を確認したうえで正式な仕様改訂によって解消する。

### PRJ-024 Constitutionとの矛盾

下位仕様が本書と矛盾する場合、その矛盾は未解決として扱う。

下位仕様を黙示的に読み替えてはならず、正式な改訂が必要である。

## 6. 仕様ID・Decision・Open Issue

### PRJ-030 仕様ID

規範仕様には安定した仕様IDを付与する。

一度外部参照に使用された仕様IDは、原則として変更・再利用してはならない。

### PRJ-031 廃止仕様

廃止された仕様IDは削除または別の意味へ再利用してはならない。

廃止状態と、必要に応じて置換先を記録する。

### PRJ-032 未確定事項

未確定の重要事項は `OPEN-<SPEC>-xxx` 形式のOpen Issueとして明示する。

未確定値をAIまたは実装担当が一般的な値で補完し、正式仕様として扱ってはならない。

### PRJ-033 Decision Log

重要な意思決定には `DEC-<SPEC>-xxx` 形式のDecision IDを付与する。

Decisionには原則として以下を記録する。

- 決定内容
- 理由
- 却下した主要案
- 影響範囲

## 7. Constitution変更管理

### PRJ-040 変更条件

本書は随時自由に書き換えてはならない。

変更する場合は、明示的なDecisionとともに、少なくとも以下を記録する。

- 変更理由
- 変更対象
- 影響する仕様
- 移行方法
- 必要な互換性対応

### PRJ-041 変更の影響確認

ConstitutionまたはAuthority仕様を変更する場合は、直接参照だけでなく、関連Invariant、依存仕様、実装契約への影響を確認する。

## 8. アーキテクチャ基本原則

### PRJ-050 Web/API責務分離

Webアプリケーションは主に以下を担当する。

- UI
- ページ
- Routing
- SSR
- SEO
- 認証UI
- API Client

正式な業務ロジックおよびDBアクセスはAPI側へ集約する。

Webから業務DBへ直接アクセスしてはならない。

Supabase Auth等、認証サービスのクライアント利用は、認証仕様で許可された範囲で例外とする。

### PRJ-051 APIを業務ルールのAuthorityとする

保護された業務操作の正式な検証・認可・状態遷移はAPI側で行う。

Web側の入力制御やUI非表示はユーザー体験向上のために利用してよいが、セキュリティ境界として依存してはならない。

### PRJ-052 過度な抽象化を避ける

AIエージェントおよび人間が追跡しやすい具体的な責務分離を優先する。

原則として以下を避ける。

- 不必要にGeneric化されたRepository
- 大規模DIコンテナ
- 不要なMicroservices
- 不要なEvent Bus
- 不要なKafka
- 必要性が説明できないRedis
- GraphQLの安易な導入
- 構成上不要なTurborepo/Nx等の追加
- 実利用のない交換可能性を目的とした過剰なAdapter層

必要性が生じた場合はDecisionを伴う設計変更として導入可能とする。

以下を本プロジェクトの標準技術構成とする。

これらは原則固定とするが、合理的理由とDecisionを伴う正式な設計変更によって置換可能とする。

外部サービス固有の概念は、合理的な範囲で連携境界へ閉じ込める。

ただし、交換可能性のみを目的とした過度な抽象化を要求しない。

## 10. データ整合性原則

### INV-PRJ-001 購入情報を失わない

決済等の外部フローへ遷移する前に、自システムが追跡に必要な状態を保持しなければならない。

ユーザーのブラウザ遷移のみを、購入・予約・決済等の確定根拠としてはならない。

### INV-PRJ-002 二重販売を成立させない

数量制約または排他制約を持つ販売対象について、競合リクエストによって許容数を超える販売を成立させてはならない。

カラオケ枠、在庫その他の排他的販売対象は、Domain仕様とDATA仕様の双方で整合性を保証する。

### INV-PRJ-003 QR・チケットの二重利用を成立させない

一回利用を前提とするチケット、QR、受付権限について、同一権利の複数回利用を正常系として成立させてはならない。

### PRJ-070 DBを最終防衛線とする

重要なInvariantは、APIの事前検証だけでなく、DB制約・Transaction・排他制御等によって可能な限りDBレベルでも保証する。

### PRJ-071 Transaction

一貫して成功または失敗すべき複数のDB更新は、一つのTransactionとして処理する。

処理途中の失敗によって、業務上不正な中間状態を永続化してはならない。

### PRJ-072 冪等性

重複実行によって金銭・権利・在庫・受付・通知等へ重大な影響が出る操作には、適切な冪等性を設計する。

冪等性はStripe Webhookだけに限定しない。

### PRJ-073 状態遷移

重要なDomain状態は許可された状態遷移を明示し、任意の`status`直接書き換えを通常操作としてはならない。

無効な状態遷移はAPIで拒否し、可能な範囲でDB整合性でも保護する。

## 11. 決済原則

### INV-PRJ-004 信頼できるサーバーイベントを決済確定根拠とする

決済確定は、ブラウザの成功ページ到達ではなく、決済事業者から検証済みのサーバー側イベント等、信頼できる証跡を正とする。

Stripe利用時の具体的なイベント、署名検証、冪等性、照合方法はPayment仕様で定義する。

### PRJ-080 決済と副作用を分離する

購入確定後のメール、通知その他の再試行可能な副作用の失敗によって、すでに確定した正しい注文・決済状態を失わせてはならない。

---

## 12. 外部サービス障害原則

### PRJ-090 外部障害を前提とする

外部サービスは一時的に失敗・遅延・重複・順序変更する可能性があるものとして設計する。

### PRJ-091 復旧可能な内部状態

外部処理が失敗しても、再試行・照合・手動復旧を行えるだけの内部状態および識別子を保持する。

### PRJ-092 再試行可能な処理の分離

メール送信等、業務確定とは独立して再試行可能な処理は、必要に応じてOutbox等の方式で主要Transactionから分離する。

具体方式は該当Technical仕様で定義する。

---

## 13. 認証・認可原則

### PRJ-100 認証と認可を区別する

ログイン済みであることは、操作権限を持つことを意味しない。

すべての保護操作についてAPI側で認可を行う。

### PRJ-101 RoleとCapability

権限モデルは、Roleと実際に許可されるCapabilityを分離できる構造とする。

個別ユーザーへの無秩序な直接権限付与を基本設計としてはならない。

### PRJ-102 最小権限

管理者・スタッフを含むすべての主体には、業務遂行に必要な最小権限のみ付与する。

### PRJ-103 強制操作

通常状態遷移を超える管理者・スタッフの強制操作は、業務上必要なものだけを明示的に定義する。

重要な強制操作では、少なくとも以下を監査可能にする。

- 実行者
- 実行日時
- 対象
- 操作前後の重要状態
- 理由

## 14. セキュリティ原則

### PRJ-110 Zero Trust at Boundary

ブラウザ、外部API、Webhook、管理画面入力、QR、URLパラメータ等、システム境界を越えて受け取る入力は信頼しない。

入力は境界で検証する。

### PRJ-111 Validation

API入力は原則としてSchemaで検証する。

標準Validation技術はZodとする。

### PRJ-112 秘密情報

以下をコード、仕様本文、Git管理対象、通常ログへ記録してはならない。

- API Secret
- Private Key
- Password
- Refresh Token
- Session Secret
- Webhook Secret
- その他の認証秘密情報

秘密情報は、承認されたSecret管理手段または安全な環境変数等で管理する。

### PRJ-113 ログへの機密情報

ログへ保存する個人情報・識別情報は必要最小限とする。

認証情報、決済カード情報、秘密鍵、パスワード等を通常ログへ出力してはならない。

### PRJ-114 QR・公開トークン

QR等の公開可能なトークンへ、推測可能なDB連番をそのまま使用してはならない。

用途ごとに推測困難なトークンを使用し、必要性がある場合はDBへトークンのハッシュを保存する。

### PRJ-115 QR検証

QRコード内の情報だけを信頼して重要な受付を確定してはならない。

通常運用ではサーバー側の現在状態を検証し、受付結果を原子的に更新する。

## 15. 監査原則

### PRJ-120 監査対象

少なくとも以下に関する重要操作は、必要に応じて監査ログ対象とする。

- 金銭
- 注文
- 返金
- チケット権利
- 受付
- 権限
- 管理者の強制操作
- セキュリティ設定
- 業務上重要なデータ変更

### PRJ-121 監査ログの保護

監査ログは通常のアプリケーション操作から任意に編集・削除できない構造とする。

具体的な保存期間、保管先、検索性はAudit/NFR仕様で定義する。

---

## 16. 個人情報・プライバシー原則

### PRJ-130 データ最小化

個人情報は、明確な利用目的があるものだけを必要最小限取得する。

将来利用する可能性だけを理由として不要な個人情報を取得してはならない。

### PRJ-131 目的限定

取得した個人情報は、明示した目的の範囲内で利用する。

新たな利用目的が生じる場合は、必要な法務・運用対応を経て仕様を更新する。

### PRJ-132 外部サービスへの送信最小化

Stripe、メール配信事業者その他の外部サービスへ送信する利用者データは、その連携に必要な最小限とする。

### PRJ-133 本番データの開発利用

本番個人データを開発環境へそのまま複製することを原則禁止する。

必要な場合は、承認された手順に基づき匿名化・最小化したデータのみ利用する。

### PRJ-134 データ保持と削除

全データを無条件に永久保存する方針は採用しない。

注文、決済、監査等の保持が必要な業務記録と、削除・匿名化可能な個人情報を区別する。

具体的な保持期間、法的保存要件、アカウント削除時の扱いは別仕様で定義する。

### PRJ-135 アカウント削除

アカウント削除が要求された場合でも、法令・会計・不正防止・監査等の理由で保持が必要な記録まで無条件に物理削除してはならない。

可能な範囲で個人識別性を低減し、保持根拠と削除可能範囲をIdentity/Privacy仕様で定義する。

---

## 17. 法務文書との境界

### PRJ-140 法務文書は別Authorityとする

利用規約、プライバシーポリシー、特定商取引法等に基づく表示その他の法務文書は、システム仕様そのものとは分離して管理する。

システム仕様が法務文書の代替Authorityとなってはならない。

### PRJ-141 法務要件の実装

法務文書によって同意取得、表示、記録、通知その他のシステム要件が生じる場合は、該当Domain仕様へ規範要件として反映する。

---

## 18. 日時・言語・通貨

### PRJ-150 内部時刻

絶対時刻は原則としてUTCで保存・処理する。

### PRJ-151 表示時刻

イベント運営および利用者向けに表示する日時は、原則として `Asia/Tokyo` を正式なタイムゾーンとする。

### PRJ-152 第一言語

日本語を本システムの正式な第一言語とする。

コード識別子、APIフィールド名、技術固有名詞等は必要に応じて英語を使用する。

### PRJ-153 国際化可能性

日本語運用を基本とするが、将来的な国際化を不必要に妨げる設計としてはならない。

ただし、現時点で全UIを多言語対応することをConstitution上の必須要件とはしない。

### PRJ-154 通貨

正式な決済通貨は原則として日本円（JPY）とする。

複数通貨対応が必要になった場合は正式な仕様変更を行う。

## 19. UI・アクセシビリティ原則

### PRJ-160 Mobile First

利用者向けUIはスマートフォン利用を第一に設計し、PC・タブレットにもレスポンシブ対応する。

### PRJ-161 Accessibility

WCAG等の一般的なアクセシビリティ原則を参考に、実用上達成可能なアクセシビリティをシステム全体の原則とする。

具体的な達成基準と検証方法はNFR仕様で定義する。

## 20. 業務設定値

### PRJ-170 業務値とコードを分離する

価格、販売期間、上限、公開状態等、運営中に変更し得る業務値は、原則としてコードへハードコードせずデータまたは設定として管理する。

### PRJ-171 Secretと業務設定を分離する

業務設定値と秘密情報を同一の管理概念として扱ってはならない。

### PRJ-172 管理画面での変更範囲

管理画面から変更可能な項目は、業務上必要なものだけを明示的に許可する。

データ整合性を破壊する可能性がある危険操作を、単に「Adminだから」という理由だけで自由化してはならない。

---

## 21. データ削除・本番DB操作

### PRJ-180 重要業務履歴

注文、決済、返金、チケット使用、受付、監査等の重要業務履歴は、通常運用で安易に物理削除してはならない。

### PRJ-181 Soft Deleteの乱用禁止

すべてのテーブルへ機械的にSoft Deleteを導入することを要求しない。

削除、取消、無効化、匿名化、履歴保持の意味をDomainごとに定義する。

### PRJ-182 本番DB直接操作

本番DBへの直接変更は通常運用として使用してはならない。

障害復旧等で避けられない場合のみ、管理された手順、実施者記録、変更内容記録、事後検証を伴って実施する。

## 22. 可用性・障害対応原則

### PRJ-190 重要時間帯

販売開始直後、イベント当日その他の停止影響が大きい時間帯を優先して、適切な可用性を確保する。

具体的なSLO等はNFR仕様で定義する。

### PRJ-191 単一障害点

重大業務を停止させる単一障害点は把握し、合理的な復旧策を用意する。

すべてを無条件に冗長化することは要求しない。

### PRJ-192 バックアップ

重要データは定期的にバックアップし、バックアップが実際に復元可能であることを確認できる運用を設計する。

### PRJ-193 復旧計画

重大障害について、少なくとも以下を別仕様で定義する。

- 復旧優先順位
- 復旧手順
- データ整合性確認方法
- 外部サービスとの再照合
- 手動対応
- 利用者・運営への必要な通知

### PRJ-194 当日ネットワーク障害

通常の受付ではオンライン状態のサーバーを正とする。

会場通信障害に備えた運用・復旧方針を別仕様で必ず定義する。

オフライン操作を許可する場合は、復旧後の整合性確認と二重利用リスクへの対処を必須とする。

## 23. Observability原則

### PRJ-200 能動的な監視

以下を含む重要状態を可能な範囲で能動的に監視する。

- アプリケーションエラー
- 可用性
- API失敗
- 決済連携
- Webhook
- 非同期処理
- 受付等の重要業務処理

### PRJ-201 アラート優先度

すべてのエラーを同じ緊急度で通知してはならない。

影響度と緊急度に応じて通知レベルを分け、重大な事象を優先する。

### PRJ-202 復旧に必要な相関情報

重要処理では、秘密情報を漏らさない範囲で、注文ID、外部決済ID、Request ID等の相関情報を用いて追跡可能にする。

## 24. 性能原則

### PRJ-210 測定可能な性能要件

重要操作は、実運用に十分な応答性能を持たなければならない。

具体的な目標値、同時利用、負荷条件、計測方法はNFR仕様で定義する。

Constitutionへ根拠のない具体秒数を固定しない。

## 25. 環境分離

### PRJ-220 環境

少なくとも以下を論理的に分離できる構成とする。

- Local / Development
- Preview / Staging
- Production

### PRJ-221 外部サービスの環境分離

決済、メール、Webhookその他の外部連携についても、可能な限り本番と非本番を明確に分離する。

非本番操作が本番利用者、本番決済、本番通知へ影響してはならない。

### PRJ-222 Seed

開発・検証に必要な代表データは、再現可能な方法で生成できるようにする。

個々の開発者が手作業でしか再現できない状態を標準運用としない。

## 26. テスト・品質保証

### PRJ-230 重要仕様の自動テスト

少なくとも以下は自動テストによる保証対象とする。

- 重要Invariant
- 状態遷移
- 認可
- 競合制御
- 冪等性
- 決済処理
- 受付
- 例外・異常系

テスト種別の詳細はTEST仕様で定義する。

### PRJ-231 回帰テスト

再現可能な不具合を修正する場合は、原則として同一不具合の再発を検出できる回帰テストを追加する。

### PRJ-232 リリース品質ゲート

本番へ反映する変更は、原則として以下の自動検証を通過しなければならない。

- typecheck
- lint
- test
- build

必要に応じてE2Eその他の検証を追加する。

## 27. DB Schema変更

### PRJ-240 Migration

DB Schema変更はMigrationとして履歴管理し、環境間で再現可能でなければならない。

本番Dashboard等からのみ行われた未管理Schema変更を通常運用としてはならない。

### PRJ-241 破壊的変更

破壊的Schema変更は、データ移行、互換期間、Rollbackまたは安全なForward Fixを考慮した段階的変更を原則とする。

## 28. API変更

### PRJ-250 API互換性

APIの破壊的変更は、既存利用側への影響を評価し、安全な移行方法を定義して実施する。

常に新APIバージョンを作ること自体は必須としない。

### PRJ-251 契約のAuthority

HTTP endpoint、request、response、error contract等の正式なAPI契約はAPI仕様をAuthorityとする。

Domain仕様は業務上必要な能力を定義し、HTTP固有構造を重複定義しない。

## 29. リリース・Rollback

### PRJ-260 Rollback可能性

重大な本番変更では、問題発生時のRollbackまたは安全なForward Fix手段を事前に考慮する。

### PRJ-261 Feature Flag

Feature Flagは、段階公開、危険度の高い変更、緊急停止等に有用な場合のみ使用する。

すべての機能へ機械的に導入してはならない。

## 30. AI/Codex実装原則

### PRJ-270 仕様をAIが勝手に変更しない

Codexその他のAI実装担当は、仕様にない重要な業務判断を独断で確定してはならない。

不明点、矛盾、実装不能条件を発見した場合は、問題として報告する。

### PRJ-271 仕様ファイルの変更

実装担当は、実装作業の都合だけで承認済み仕様ファイルを変更してはならない。

仕様変更が必要と判断した場合は、変更提案として分離する。

### PRJ-272 仕様と実装の不一致

仕様と実装が矛盾する場合は、原則として承認済み仕様を正とする。

実装差異は、不具合または仕様変更候補として扱う。

### PRJ-273 実装範囲

Codexへ渡す各実装プロンプトは、参照する仕様と今回の実装対象を明確にしなければならない。

未実装の正式仕様が存在することは、仕様の削除・簡略化理由にはならない。

### PRJ-274 実装の可読性

AIおよび人間が追跡しやすい以下のコードを優先する。

- 小さく具体的な関数
- Domain用語と一致した命名
- 明確な責務境界
- 型による制約
- 明示的な状態遷移
- テスト可能な構造

### PRJ-275 変更範囲の最小化

実装担当は、依頼された目的に必要な変更範囲を超えて無関係なリファクタリングや仕様変更を行わない。

## 33. 最重要System Invariants

排他的販売対象または有限在庫について、許容数を超える成立済み販売状態を作ってはならない。

保護された業務操作は、クライアントUIではなくサーバー側認可によって保護しなければならない。

### INV-PRJ-014 Recoverability

重要業務処理は、外部障害や部分失敗後に追跡不能な状態へ陥ってはならない。

### INV-PRJ-015 Auditability

金銭・権限・受付・強制操作等の重要な管理操作は、必要な範囲で後から追跡可能でなければならない。

## 35. Decision Log

### DEC-PRJ-001 Constitutionの拘束力

**決定:** 本書を全仕様・実装が従う最上位ルールとする。

**理由:** 仕様の長期的一貫性と、実装担当による暗黙の設計変更を防止するため。

### DEC-PRJ-002 技術スタックの変更可能性

**決定:** 標準技術を原則固定し、理由・影響範囲を明示したDecisionによる変更を許可する。

**理由:** 技術的一貫性を維持しつつ、長期運用で必要な更新余地を残すため。

### DEC-PRJ-003 Authorityモデル

**決定:** Constitutionを最上位とし、それ以外は概念ごとのAuthority所有仕様を正とする。

**理由:** 作成順や文章の具体性による曖昧な優先順位を排除するため。

### DEC-PRJ-004 他領域の再定義禁止

**決定:** Authorityを持たない仕様は他領域の規範を再定義せず、正式仕様IDを参照する。

**理由:** 同一ルールの重複と仕様間ドリフトを防止するため。

### DEC-PRJ-005 仕様と実装の分離

**決定:** 正式仕様は完成形を記述し、実装範囲は実装プロンプトで制御する。

**理由:** 長期仕様を短期的な開発順序から独立させるため。

### DEC-PRJ-006 Web/API分離

**決定:** 正式な業務ロジックとDBアクセスをAPIへ集約する。

**理由:** 認可・整合性・監査・保守性を一つの境界で保証しやすくするため。

### DEC-PRJ-007 重要InvariantのDB保証

**決定:** 重要InvariantはAPIだけでなく、可能な限りDB制約・Transaction・排他制御でも保証する。

**理由:** 競合や実装ミスに対する最終防衛線を持つため。

### DEC-PRJ-008 冪等性の横断適用

**決定:** 重複実行で重大な副作用が生じる処理全般に冪等性を要求する。

**理由:** 二重課金・二重発行・二重受付等を横断的に防止するため。

### DEC-PRJ-009 監査可能な強制操作

**決定:** 必要な管理者強制操作は許可するが、理由・実行者・変更内容を監査可能にする。

**理由:** 現場運用の柔軟性と統制を両立するため。

### DEC-PRJ-010 データ最小化

**決定:** 明確な目的のある個人情報のみ取得し、外部サービスへの送信も最小化する。

**理由:** 情報漏えい時の影響と不要なデータ管理コストを減らすため。

### DEC-PRJ-011 イベント再利用性

**決定:** 特定イベントへ最適化しつつ、同系統イベントへの再利用を妨げない設計とする。

**理由:** 過剰な汎用化を避けつつ、将来の継続開催へ備えるため。

### DEC-PRJ-012 Mobile First

**決定:** 利用者向けUIはスマートフォンを第一に設計する。

**理由:** 購入・電子チケット・会場利用でスマートフォン利用が中心になるため。

### DEC-PRJ-013 時刻と通貨

**決定:** 内部絶対時刻はUTC、利用者・運営表示はAsia/Tokyo、通貨はJPYを原則とする。

**理由:** 日本開催イベントとして時刻解釈と会計を一意にするため。

### DEC-PRJ-014 環境分離

**決定:** 本番と非本番、および外部サービスの本番・テスト環境を明確に分離する。

**理由:** テスト操作が実利用者・本番決済・本番通知へ影響する事故を防ぐため。

### DEC-PRJ-015 AI実装権限

**決定:** AI実装担当は承認済み仕様を独断で変更・補完せず、重要な不明点は報告する。

**理由:** 実装都合で仕様が事実上変更されることを防ぐため。

## 37. Handoff

### 37.1 この仕様書で確定した事項

- 正式仕様は完成形・長期運用を記述する。
- 実装範囲は仕様ではなく実装プロンプトで制御する。
- Constitutionを全仕様・実装の最上位Authorityとする。
- Constitution以外は概念ごとのAuthority所有仕様を正とする。
- Authorityを持たない仕様は他領域を再定義しない。
- 承認済み仕様ファイルを実装のSingle Source of Truthとする。
- WebとAPIを分離し、業務ロジック・DBアクセス・認可をAPI側へ集約する。
- 重要Invariantは可能な限りDBレベルでも保証する。
- Transaction、冪等性、許可された状態遷移を重要設計原則とする。
- 購入情報ロスト、二重販売、二重利用をシステム全体の重大事故として防止する。
- 管理者強制操作は必要最小限かつ監査可能とする。
- 個人情報は最小限収集し、外部サービスへの送信も最小化する。
- 本番DB直接操作を通常運用として禁止する。
- 環境を本番と非本番に分離する。
- 重要Invariant・異常系・認可・競合等を自動テスト対象とする。
- Codexその他のAI実装担当は仕様を独断で変更しない。
- 1 Chatにつき1仕様ファイルを原則とし、各ファイル末尾にHandoffを持つ。

- `INV-PRJ-001`: 購入情報を失わない。
- `INV-PRJ-002`: 排他的販売対象を二重販売しない。
- `INV-PRJ-003`: 一回利用権利を二重利用させない。
- `INV-PRJ-004`: ブラウザ遷移だけを決済確定根拠にしない。

### 37.3 後続仕様への要求

#### SYS / System Overview
- 本書の責務分離と主要システム領域を具体的なシステム境界へ落とし込む。
- 外部システムとの境界を整理する。

#### GLO / Glossary & Domain Language
- 仕様横断で使用する正式用語を定義する。
- 同義語・禁止語・状態名称の揺れを防止する。

#### NFR / Non-functional Requirements
- 可用性、性能、バックアップ、RPO/RTO相当の具体基準を定義する。
- Accessibilityの具体的目標を定義する。
- ログ・監視・保持期間の具体要件を定義する。

#### Domain Specs
- 各業務概念のAuthorityを明示する。
- 状態遷移、競合、異常系、監査、受け入れ条件を規範化する。
- 本書のInvariantを破らない。

#### DATA
- Domain InvariantをDB制約、Index、Transaction、Lock等へ変換する。
- 物理データモデルのAuthorityとなる。

#### API
- Domain能力をHTTP/API契約へ変換する。
- 認証・認可・Validation・Error Contractを一貫させる。

#### SEC / Authorization
- Role / Capability / Least Privilegeを具体化する。
- 秘密情報、Token、Rate Limit等の詳細を定義する。

#### TEST
- 仕様IDとテスト要件を対応付ける。
- 重要Invariantの競合・重複・障害テストを定義する。
